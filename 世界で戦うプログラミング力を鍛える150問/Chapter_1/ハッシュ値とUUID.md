
## 余談：完全に重複排除を行いたい要請があるとして、実現は可能なのか
数学的には不可能。鳩の巣原理により、入力空間より出力空間の方が大きければ必ずどこかで衝突する。

1. キー集合が事前に固定されているなら Perfect Hashing 
コンパイラの予約語判定や辞書の静的な語彙集合など、対象キーが既知で変化しない場合は、その集合専用に衝突ゼロのハッシュ関数を構築できる。（gperfは、完全なハッシュ関数を生成するためのツールです。文字列の集合を入力として受け取り、その文字列を高速に検索できるハッシュ関数を生成します。）
Minimal Perfect Hashing なら出力空間もキー数ぴったりに詰められる。

2. 出力空間を十分大きくして「確率的にゼロ」にする
- 汎用の可変長入力（ファイル内容など）には使えないので、SHA-256のような暗号学的ハッシュで出力を巨大にし、誕生日問題の確率を天文学的に低くする。
- Git や IPFS などのコンテンツアドレッシングはこの方式で、「理論上はゼロではないが実質無視できる」を前提にしている。
- 

3. 衝突を検出してフォールバックする
ハッシュが一致しても実データ同士を比較して確定させる。
ハッシュテーブルの実装（チェイニング/オープンアドレッシング）や重複排除システムはこの「衝突前提で対処する」設計。
ハッシュは「候補の絞り込み」に使い、最終判定は生データで行う。

4. そもそもハッシュを使わず一意性を保証する
真の一意性が必須（主キー、トランザクションIDなど）ならハッシュではなく UUID や連番の自動採番、あるいはロック付きの採番サービスを使う。ハッシュは「同じ入力なら同じ出力」は保証するが「異なる入力なら異なる出力」は保証しないため、一意性が要件ならハッシュに頼るべきではない。

まとめると、キー集合が固定なら perfect hashing、そうでなければ「衝突確率を無視できるレベルまで下げる」＋「衝突検出時のフォールバック」の組み合わせが現実的な落とし所。

## メモ置き場
ある特定のキーワードとマッチするかどうかを判定するようなプログラムを書く場合，力任せにマッチさせてもいいのだが，効率よくマッチさせるにはハッシュ法を用いれば良い．

ID生成・採番系
- 連番/シーケンス(Auto-increment) — DBが順番に払い出す
- UUID/GUID — ランダム性で衝突確率を無視できるレベルまで下げる
- Snowflake ID / ULID — 時系列ソート可能な分散ID生成方式

分散システム・データ配置系
- パーティションキー/シャーディングキー — データをどのノード/シャードに置くか決める

データ構造系
- ハッシュテーブルのキー / 辞書(Map)のキー — 値を取り出すための識別子
- インデックス
その他運用系
- キャッシュキー — キャッシュの保存/参照に使う識別子
- 冪等性キー(Idempotency Key) — 同じリクエストの重複実行を防ぐ

ちょっと訂正が必要で、ハッシュと「採番」は性質が違う。

### ハッシュ値
- 採番(連番・UUID・Snowflake ID)は、内容とは無関係に一意性を保証するために新しく値を発行する仕組み。
- ハッシュは、内容から決定的に導出される値で、「同じ内容なら必ず同じ値になる」のが本質。一意性を積極的に保証するものではなく、前回の質問の通り衝突もあり得る。
「内容から決定的にキーを導出する手段」で、UUIDなどのランダム採番とは別カテゴリと捉えるのが正確。

本質的な軸は「決定性」
- ハッシュは同じ値に対して決定的。同じ入力は常に同じ出力を変えす。
    - Gitが同じファイル内容なら誰の環境でも同じblobハッシュになるのはハッシュ値を採番しているから

### 体感的に、ハッシュ値は衝突しなければしないほど良さそう
衝突耐性だけを見ると、
```md
SHA-512 > SHA-256 > SHA-1
```
となる。

しかし、長いハッシュにはコストがかかります。
SHA-1は160ビットなので20バイトです。
SHA-256は256ビットなので32バイトです。
```md
SHA-1   : 20バイト
SHA-256 : 32バイト
```
1個なら12バイト差なので些細です。

でも、Gitのように大量のオブジェクトIDを、

ディスクに保存する
treeやcommitに埋め込む
ネットワークで送る
メモリに載せる
インデックスで検索する

となると、差が積み重なります。

判断軸は「でかいシステムか」より、

- 何件くらい扱うか
- 衝突したら何が壊れるか
- 衝突を後から検出・解消できるか
- 悪意ある入力を受けるか
- ハッシュを何十億個保存するか

あたりになります。

- UUID = 発行された切符
    - 内容とは無関係に、生成した瞬間の乱数（やタイムスタンプ）で決まる
    - 同じデータに対して2回UUIDを発番したら別物として扱われる「内容の同一性」の検証
    - その代わり「唯一無二の新規IDを今ここで発行したい」という目的には最適で、衝突は「独立に振ったIDがたまたま被る確率」の問題に還元される
    
   
面白いのは、この2つが衝突の意味合いも違うという点。ハッシュ衝突は「本質的に有限の出力空間に無限の入力を押し込む」構造的な必然。UUID衝突は「十分広い空間からランダムに引いたら偶然被った」という確率の話——同じ「衝突」という言葉でも、片方は設計上避けられない前提、もう片方は限りなくゼロに近づけられる運の問題、という違いがある。

もう一段実務的な言い方をすると、「同一性を検証したいならハッシュ、新規性を主張したいならUUID」という使い分けになる。同じデータに繰り返し同じキーを振りたい（冪等性、重複排除、キャッシュ）ならハッシュ、毎回違うものとして新しく採番したい（新規レコード、トランザクション）ならUUID、という感じ。

**ハッシュ値が活用されるシーン**

| シーン | 用途 |
|---|---|
| コンテンツアドレッシング | Gitのblob/commitハッシュ、Dockerイメージのdigest、IPFSのCID — 「内容そのものがID」 |
| 重複排除(dedup) | 同じファイル/ブロックを保存する前にハッシュで既存判定 |
| 改ざん検知・整合性検証 | ダウンロードファイルのSHA256チェックサム、TLS証明書のフィンガープリント |
| パスワード保存 | bcrypt/scrypt/argon2などソルト付きハッシュで平文を保存しない |
| キャッシュキー生成 | リクエストパラメータやクエリをハッシュ化してキャッシュのキーにする |
| ハッシュテーブル/連想配列 | Map・Dictionary・Setの内部実装（バケット決定） |
| コンシステントハッシュ法 | 分散キャッシュ(Memcached等)やシャーディングで担当ノードを決める |
| デジタル署名 | 署名前にメッセージダイジェストを取る(RSA署名など) |
| ブロックチェーン/Merkle Tree | ブロック同士の連結、改ざん検知 |
| HTTPのETag | レスポンス内容のハッシュでキャッシュ有効性を判定 |

**UUIDが活用されるシーン**（内容と無関係に新規発行する性質を使う）

| シーン | 用途 |
|---|---|
| DBの代理キー | マイクロサービス/分散DBで中央採番サーバなしに主キーを発行 |
| セッションID/トークン | ログインセッションの識別子 |
| リクエストID/トレースID | 分散トレーシング(OpenTelemetry等)でリクエストを横断追跡 |
| 冪等性キー(Idempotency-Key) | 決済APIなどで同一リクエストの重複実行を防ぐ |
| アップロードファイル名 | ファイル名衝突を避けてストレージに保存 |
| イベントID/メッセージID | メッセージキュー(Kafka, SQS等)でのイベント一意識別 |
| デバイスID/インストールID | モバイルアプリの端末・インストール単位の識別 |
| マルチマスタレプリケーション | オフラインファーストアプリ等、複数拠点で独立に採番しても衝突しない |
| COM/.NETのGUID | オブジェクト・インターフェースのグローバル一意識別 |

**見分け方のショートカット**: 「内容が同じなら同じ値にしたい」→ハッシュ、「発行するたびに新しい別物にしたい」→UUID、という軸で分類すると迷わない。



### 　ハッシュの具体例： blobハッシュ
- Gitのオブジェクトには blob / tree / commit / tag の4種類がある。
- blob = ファイルの中身（バイト列）そのものを表すオブジェクト。
- ファイル名・パス・パーミッションといった「メタ情報」は一切含まれず、純粋に中身だけがハッシュ化対象になる。
```
sha1("blob " + 内容のバイト数 + "\0" + 内容そのもの)
```
なので、ファイル名やディレクトリが違っても中身が1バイトも違わなければ同じblobオブジェクトになる。
逆に改行1つ違うだけでも全く別のハッシュになる。
こういう仕組みは **コンテンツアドレス方式** という言い方もできる。
Gitのblobは差分(diff)を保存しているわけではない。「変更」という概念はcommit同士を比較したときに初めて（git diffが計算して）出てくるものであって、blob自体は常にその時点のファイル内容の完全なスナップショットを表す。

だから正確には:
- 「同じ変更をした」から同じハッシュになるのではなく、「変更した結果の最終的な中身がバイト単位で一致した」から同じハッシュになる
- 全く無関係な経緯（別のブランチ、別の人が独立に書いた、コピペした等）で作られたファイルでも、最終的な中身さえ一致すれば同じblobオブジェクトを指す
- 逆に、同じ「1行追加する」という論理的に同じ変更でも、追加先のファイルの元の中身が違えば結果の中身も違うので、別のblobになる

この性質のおかげで、Gitは同じ内容のファイルを複数のcommitや複数パスで使い回していても、内部的には1個のblobオブジェクトを共有するだけで済む（ストレージの重複排除）。treeオブジェクト（ディレクトリ構造）が「このパスにはこのblobハッシュ」という対応表を持つことで、ファイル名とファイル内容が分離されている、というのがGitのオブジェクトモデルの肝。
